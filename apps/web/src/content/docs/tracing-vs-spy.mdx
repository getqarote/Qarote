# Tracing vs Spy

Qarote gives you two ways to watch what's happening on your broker:

- **Tracing** is a broker-wide audit log — metadata for every publish and delivery, persisted for days, queryable.
- **Spy** is a stethoscope on one queue — full message bodies, live, ephemeral.

Both show messages flowing, but they answer different questions and cost very different amounts. This page helps you pick.

## At a glance

|                         | **Tracing**                                   | **Spy**                                          |
| ----------------------- | --------------------------------------------- | ------------------------------------------------ |
| **Question it answers** | _What happened on my broker?_                 | _What's flowing through this queue right now?_   |
| **Scope**               | Whole vhost                                   | One queue                                        |
| **Persistence**         | Stored in Qarote (default 7 days)             | In-memory; session expires 90 s after disconnect |
| **Message body**        | Metadata only (routing key, size, timestamps) | Full payload                                     |
| **Activation**          | Always on once enabled                        | On demand, per session                           |
| **Broker overhead**     | 5–15 % CPU at high message rates              | Negligible                                       |
| **Workspace-visible**   | Yes — every member sees the same data         | No — your browser session only                   |

## How they work

Both features take a side path off the same broker exchange — but the path looks very different.

### Tracing

The `rabbitmq_tracing` plugin makes the broker copy every published and delivered message to the `amq.rabbitmq.trace` exchange. A Qarote background worker consumes that exchange and stores metadata in PostgreSQL with a configurable retention. Capture continues whether or not anyone has the dashboard open.

### Spy

<Mermaid
  ariaLabel="Spy data flow: Qarote opens a temporary shadow queue bound to the same exchange, streams matching messages to the browser, and tears the queue down on session end."
  code={`flowchart LR
    P([Producer]) --> X[Exchange]

    Q --> C([Consumer])
    X -.duplicate.-> S[qarote.spy.&lt;id&gt;<br/><i>shadow queue,<br/>auto-deleted</i>]
    S --> Tap[Qarote tap session]
    Tap --> Br[Browser<br/><i>RAM only, expires<br/>90 s after disconnect</i>]

    classDef normal fill:#f5f5f5,stroke:#999,color:#333
    classDef qarote fill:#e8f1ff,stroke:#3366cc,color:#1a3a7a
    class P,X,Q,C normal
    class S,Tap,Br qarote`}

/>

When you start a Spy session, Qarote opens an AMQP connection, creates a temporary shadow queue bound to the same exchange as the target queue, and streams matching messages to your browser. Stop the session (or close the tab) and the shadow queue is auto-deleted. Nothing reaches PostgreSQL, nothing is shared with other workspace members.

## When to use which

### Reach for **Tracing** when

- You need to look at the past. _"What was published to `orders._` yesterday between 14:00 and 14:30?"\*
- You're triaging a slow-burn issue and don't yet know which queue is at fault.
- You want a continuous record of broker activity for audit or postmortem.
- You need to compare patterns over time (publish rate this morning vs last week).

### Reach for **Spy** when

- You need actual message bodies to verify the publisher is sending what you expect.
- A queue is misbehaving _right now_ and you want to peek at the next few messages.
- You're debugging a single producer or consumer in isolation.
- The `rabbitmq_tracing` plugin is disabled and you can't (or don't want to) enable it.

### Use them together

Real workflows rarely use just one. Example:

1. A user reports that payments are silently failing.
2. **Tracing → History**: filter on exchange `payments` for the last hour. You see 200 publishes but only 150 deliveries — 50 messages went somewhere they shouldn't.
3. The metadata shows the unrouted messages all targeted `payments.failed`. You suspect that queue.
4. **Spy** on `payments.failed`: open a session, watch the next ten messages arrive. The bodies show `amount: null` — the producer has a bug.

Tracing told you _where to look_. Spy told you _what's actually broken_.

## Cost and impact

### Tracing

Enabling Tracing turns on RabbitMQ's `rabbitmq_tracing` plugin on the chosen vhost. The broker copies every published and delivered message to an internal exchange that Qarote consumes. Two costs to know:

- **Broker CPU**: typically 5–15 % overhead at sustained high message rates (>10 k msg/s). Measurable but not destructive — disable it any time and the overhead vanishes.
- **Qarote storage**: every captured event becomes a row in Qarote's database. Default retention is 7 days; older events are pruned automatically.

<Callout type="warning" title="Best-effort under load">
  Tracing is best-effort by design. Under sustained broker overload, RabbitMQ
  may drop trace messages before Qarote captures them. The Tracing health badge
  in your dashboard shows current capture lag and any drops in the last hour, so
  you always know what you're seeing — and what you're missing.
</Callout>

### Spy

Spy enables no plugins and stores nothing beyond the live session. It opens a temporary binding from the queue's exchange to a short-lived shadow queue, reads from the shadow, and tears it all down when you stop. The only cost is the bandwidth of duplicating matching messages while the session is active. See [Spy on live queues](/docs/queues/spy-on-live-queues/) for the full mechanism, requirements, and limitations.

## Choosing in two questions

Two questions usually settle it:

1. **Do you need the message body?** → **Spy.** Tracing only captures metadata.
2. **Do you need to look at the past?** → **Tracing.** Spy only shows what arrives during the session.

If the answer to both is no — you just want a live, broker-wide view of metadata-level traffic — open Tracing's **Live tail** tab.
